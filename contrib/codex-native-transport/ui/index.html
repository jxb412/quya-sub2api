Codex Native Transport

使用固定版本的 Rust reqwest + native-tls + hyper/h2 出站。应用层身份默认由 Sub2API 宿主管理，插件主要负责原生传输、连接池和 Cookie 隔离。

指纹隔离

默认开启。每个账号拥有独立连接池、稳定 installation-id 和 Cloudflare Cookie，避免多个 OAuth 账号共用同一设备环境。

machine 会把已有 session/thread/window/prompt_cache_key 按账号做稳定 1:1 映射；不会把所有用户压成一个会话，也不会凭空添加身份字段。

实验功能，默认关闭。开启后每个请求重建 session/thread/cache key 并剥离 turn-state，会降低缓存命中并破坏远端会话延续，只用于短期故障排查。

身份 Profile
版本自动同步

默认关闭。自动同步只更新 UA/version 文本，不会更新已编译的 TLS/HTTP2 依赖；网络栈升级仍必须重新构建插件。

传输

自动捕获并回放 __cf_bm / _cfuvid 等 Cloudflare 基建 Cookie（白名单与 Codex 源码一致，绝不保存账号/会话 Cookie）；隔离粒度由上方"一账号一指纹"开关决定。

管理面板

填 127.0.0.1:8848 只能本机访问；需要远程查看就填 0.0.0.0:8848（同时要在防火墙/安全组放行该端口）并务必使用强 token。面板只展示账号列表与巡检结论，不含任何凭据。

宿主管理 API

智力巡检与降智通道都要靠它枚举账号、取 access_token、暂停/恢复调度。插件与宿主同容器时用 http://127.0.0.1:8080。

账号智力巡检（降智检测 + 自动暂停）

总开关。关掉后连面板里的手动「检测」也不能用。

只控制「按间隔自动跑」。与总开关不冲突：总开关关 = 全停；总开关开 + 本项关 = 只能手动检测；两项都开 = 手动可用且按间隔自动跑。

面板里对单个账号开启了「降智处理」的，自动暂停会跳过它（改走降智通道）。

回答里命中任意一个关键词即判「不合格」。建议除了 2024 再加上「无法确认 / 没有提供 / 无法确定」这类拒答措辞：降智号有时不提 2024，只说「我不知道自己的知识截止日期」，只用单一关键词会被误判成合格。

勾上后：回答里没有 19xx/20xx 年份就判「不合格」。降智号除了答 2024，还会答「我不知道自己的知识截止日期」这种不含任何关键词的敷衍话，只靠关键词会把这种号误判成合格、又切回正常通道。

超时＝等满「单次提问超时」仍拿不到可判定内容（含重试全部用完）；勾上后按不合格处理（默认勾选，避免巡检卡住时把坏号当好人）。每次失败会重试「提问失败重试次数」次，间隔 0.8 秒。连续合格次数＝巡检连续 N 次判「合格」才算真的恢复（防抖动）。

巡检借一条真实 Codex 流量做请求形状，因此需要先有真实业务流量经过插件。

降智账号 BPS 通道（实验，默认关）

BPS 端点回 403（账号被上游拦截）时，把这个账号上配置的这几个模型从后台账号的模型名单里摘掉，同分组其它账号照常接；时间到自动加回。默认开，默认 gpt-6-astra, gpt-5.6-sol。

切换节奏（让客户端不掉缓存）：
1) 恢复后保持期：巡检连续「连续合格次数」次判合格后，账号不会立刻切回，而是继续走 BPS 直到保持期结束，避免在临界点来回跳；填 0 = 一合格就切回。
2) 同会话粘滞：同一个会话（按 prompt_cache_key / 会话 id 派生）在粘滞时长内固定走同一条通道，一轮对话中途不会换上游，prompt cache 不会断；填 0 = 每个请求重新判定。
3) BPS 失败冷却：走 BPS 建连/HTTP 失败时，本次请求立刻改用原通道补发（客户端无感），并按错误类别给该号设一段不同的冷却时间（可分别设置 超时/连接失败、400、401、403、429，其它状态码用最后一项兜底；填 0 = 该类错误不冷却）。这样偶发 400 不会像 403 那样长时间禁掉一个号。
4) 每账号每日 BPS 次数上限：该号每自然日（UTC）最多能真的打多少次 BPS 端点，超了就从下一条起走正常通道，只在巡检页留一条原因；填 0 = 不限。用于防止某个号一天内把上游配额打爆。

面板里对单个账号点「降智处理」后：该号智力不合格**不再被自动暂停**，而是把上面这些模型的请求改走 BPS 端点，直到该号恢复合格。出站按上游白名单重写请求体（剥掉 tools / tool_choice / text / include / temperature / previous_response_id 等，store 固定 false，metadata 只留 task_id + turn_id），客户端工具目录与调用协议写成一条 developer 消息；模型按协议输出的一行 JSON 会被回程翻译成标准 function_call。
三种桥接方案（随时可切换，不用改客户端）：
• text：历史里的工具调用/结果转成文本消息，模型用一行 JSON 协议请求工具（默认，实测最稳）。
• native：历史里的 function_call / function_call_output 按原生 Responses item 形状回放，调用载体仍是一行 JSON 协议（ghcp_proxy 的 native 路线，工具状态机更自然）。
• officejs：在 native 基础上，让模型调用上游 Excel 插件的 run_officejs，把真正的工具请求写进它的 code 字段，代理拦截还原（上游当前未声明 run_officejs 时会自动退化成一行 JSON 协议）。
同一会话按 prompt_cache_key 派生稳定 task_id / turn_id，第二轮起命中上游缓存（实测 cached_tokens ≈ 99%）。⚠️ 单次请求输入开销约 17k token，建议只对确实被限流的账号开启；先用每行的「BPS自检」确认能拿到 2xx。（Business Premium 类型账号在这个总开关打开时默认勾选降智处理，新增账号约 1 分钟内自动套上；手动关掉的账号不会被自动打开。）

跨机状态同步（多台服务器共用同一批账号）

两台服务器如果共用同一批账号（同一份数据库），同一个账号在两台上是同一个上游身份，面板里那个「降智处理」开关理应两台一致。
开启后：本机改动立刻推给对端，并按「对账周期」定期全量对齐；对端收到后只落自己的状态、不再回推，所以不会来回震荡。
每个账号按改动时间取新（last-write-wins）——两台都是旧数据时以「勾上降智处理」的那台为准。
只同步开关本身；线路统计（成功/失败次数）是每台自己的流量，不参与同步。对端不可达只影响这条同步链路，客户端请求不受影响；失败原因在 /api/status 的 sync 字段里。
