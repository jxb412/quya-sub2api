# Quya v0.2.25 同步与已购续期提前启用

日期：2026-11-24。生产基线 `fd73a29111a8`，官方稳定发布 `v0.2.25`，Quya 候选版本 `0.4.29-quya.1`。

## 官方合并与自定义保留

官方合并提交 `48394859c`，包含 API Key 请求头身份变量、上游分组信息同步、计费接口分组信息、OpenAI HTTP 400 结构化错误透传与脱敏、compact 过载错误分类和 WebSocket 依赖修复。

合并时补齐官方新请求头变量与 Quya HTTP→WS ctx_pool 的交叉兼容：连接握手不能保留单次请求的 request_id；稳定用户、Key、分组身份必须参与连接隔离。连接失败后的 HTTP 兜底仍使用该 HTTP 请求自己的头及日志。

保留原有功能：

- ctx_pool 选定时 HTTP/SSE 转上游 WS，首次连接加3次重试、每次5秒；发送生成前可 HTTP 兜底，发送后禁止自动重放。
- GPT-6.2 稳定 developer 指令前缀、旧模型和 compact 兼容。
- 调度快照中的入口能力、Responses-only、Codex 客户端限制。
- 官方内容哈希逻辑，Quya 风控 PRO/pro20/pro200/pro500 等类型匹配。
- Gemini Neon/Hydrogen 模型与隐式缓存价格归一化，管理员自定义价优先。
- 共享 Redis 启动时保留其他实例正在使用的并发状态。
- #8999 的 browser_tabs/terminal_info 明文上下文兼容及普通工具调用严格校验。
- 禁止默认安装、启动初始化及订阅自动额度重置。

本次官方更新没有通用加密 function output 解密恢复能力，不能据此宣称已解决此前密文错误或 OAuth token_revoked。

## 用户确认的业务规则与数据来源

2026-11-25调整：全部在 Sub2API 用户订阅页面完成，不新增 PHP 页面，也不要求升级 PHP 网站。以本地用户充值记录中的成功订阅兑换、订单号、分组、实际天数及订阅来源链核对权益。

1. 当前订阅有效且精确剩余时间大于31×24小时。这是入口条件，不能单靠天数推断可重置次数。
2. 核对 `redeem_codes` 的 `store_` 购买码、`store order <订单号>` 备注、used状态、使用者、分组、实际30/31天、兑换时间；结合原订阅备注、历史订阅及重置回执确定当前一期和排队续购。
3. “同套餐”按 Sub2API 同一订阅分组和实际购买周期核对。商城商品SKU、实时支付状态及未提交到 Sub2API 的退款意图不在本地数据中，不宣称核验这些字段。
4. 结束当前一期，放弃其剩余时间和额度，从操作成功时完整启用最早一份续购。后续购买保持排队，总期限为全部待启用购买天数之和。
5. 例如旧期剩20天＋续购30天＝共50天，重置后剩完整30天；另有31天续购则共剩61天，其中31天继续排队。
6. 已消费、已退款、赠送或手动延长导致来源无法对应、历史缺失或歧义的权益不能自动重置。每份续购只可提前启用一次。

## 原生页面与接口

- 用户订阅卡片“重置订阅”按钮打开站内确认弹窗。显示当前订单、下一笔订单、实际天数、排队份数、重置前后到期时间及放弃权益提示；不传出登录凭据，不嵌入商城页面，不显示原始兑换码。
- `GET /api/v1/subscriptions/:id/reset-preview`：仅允许登录用户查询自己的订阅，返回服务端核验的预览。
- `POST /api/v1/subscriptions/:id/reset`：只接收 `preview_token` 和 `accepted_rules=true`；用户、分组、购买码由服务端推导，不接受浏览器指定。
- 执行前重新读取来源和订阅状态，预览凭据绑定同一次操作。重复点击、响应丢失后重试返回同次回执，不消耗后续另一笔续购。
- 设置 `subscription_reset_enabled` 默认为false。用户和管理员的新激活接口都在服务端检查此开关，读取设置失败时拒绝执行；直接访问接口不能绕过。旧 `subscription_reset_url` 不再使用。
- 原管理员 `activate-renewal` 接口保留兼容，同时执行本地来源核验；只读 `renewal-activation` 回执查询不受开关影响。
- 保持 `subscription_maintenance.auto_reset_enabled=false`。自动周期清零开启时不提供新自助重置。

## 与原 PHP 插件兼容

原 PHP 继续使用既有分配、撤销和充值接口。保护逻辑统一放在 Go 后端，按用户的数据库事务锁协调原生重置、旧重开分配和订单退款入账；检查历史记录时包含已撤销订阅，不能只看活动列表。

旧退款调用仅带用户、购买码派生的 `sbr_` 代码、金额和订单号，没有原订阅ID和报价快照。跨期情况下，旧退款恢复和新期合法退款可能形成完全相同的请求，后端无法凭这些字段证明金额应归哪一期。对此拒绝自动入账并提示管理员核对，不猜测、不重复发放。用户确认弹窗会提示重置后的历史套餐余额转换可能需要客服核对。普通未重置套餐和常规充值应保持原有行为。

迟到请求仍在其原订阅结算；只有具有重置回执的已撤销旧期允许此类结算。Redis额度缓存携带订阅ID与版本屏障，防止旧期费用和过期异步快照进入新期。

## 数据库与发布准备

官方 v0.2.24→v0.2.25没有新增迁移。本功能新增253回执表：`253_quya_subscription_renewal_activations.sql`。不回填猜测的历史购买次数，不初始化数据库，不直接改现有余额、额度或期限。

发布顺序：

1. 在隔离环境验证迁移和并发测试；保留可回退的应用版本。
2. 对共享数据库执行并按现有流程登记253迁移文件及SHA-256，只执行一次。新版订阅计费和撤销依赖此表，必须在接流量前完成；保持禁止启动初始化。
3. `subscription_reset_enabled=false` 下升级两台 Go 服务，确认同版，排空旧请求与计费worker。共享缓存混版时不得开放重置。
4. 使用专用测试用户和订单验证充值记录、原生确认页面、连续多份续购、旧插件正常分配及退款保护。
5. 最后由管理员打开“订阅自助重置”开关。无需上传任何 PHP 文件、配置商城 URL 或新增跨站登录。

需要停用时关闭开关即可阻止新的预览和执行。已经完成重置后，不能直接回滚到缺少来源/回执保护的旧计费、分配、退款代码；应保留这些兼容保护和回执表，不删除已消费的权益记录。
