# Quya v0.2.25 同步与已购续期提前启用

日期：2026-11-24。生产基线 `fd73a29111a8`，官方稳定发布 `v0.2.25`，Quya 候选版本 `0.4.29-quya.1`。

## 官方合并与自定义保留

官方合并提交 `48394859c`，包含 API Key 请求头身份变量、上游分组信息同步、计费接口分组信息、OpenAI HTTP 400 结构化错误透传与脱敏、compact 过载错误分类和 WebSocket 依赖修复。

合并时补齐官方新请求头变量与 Quya HTTP→WS ctx_pool 的交叉兼容：连接握手不能保留单次请求的 request_id；稳定用户、Key、分组身份必须参与连接隔离。连接失败后的 HTTP 兜底仍使用该 HTTP 请求自己的头及日志。

保留原有功能：

- ctx_pool 选定时 HTTP/SSE 转上游 WS，首次连接加3次重试、每次5秒；发送生成前可 HTTP 兜底，发送后禁止自动重放。
- GPT-6.2 稳定 developer 指令前缀、旧模型和 compact 兼容。
- 调度快照中的入口能力、Responses-only、Codex 客户端限制。
- 官方内容哈希逻辑，Quya 风控 PRO/pro20/pro200/pro500 等类型匹配。
- Gemini Neon/Hydrogen 模型与隐式缓存价格归一化，管理员自定义价优先。
- 共享 Redis 启动时保留其他实例正在使用的并发状态。
- #8999 的 browser_tabs/terminal_info 明文上下文兼容及普通工具调用严格校验。
- 禁止默认安装、启动初始化及订阅自动额度重置。

本次官方更新没有通用加密 function output 解密恢复能力，不能据此宣称已解决此前密文错误或 OAuth token_revoked。

## 用户确认的业务规则

“重置订阅”是提前启用已付款续购，沿用原 PHP 插件的语义。

1. 订阅有效且精确剩余时间大于31×24小时；只作为入口条件，不用剩余天数推断订单数量。
2. 商城验证每个来源订单已付款、履约成功、属于同一会员及同一套餐商品和分组，并与已使用兑换码、实际购买天数对应。
3. 使用最早的一份尚未启用续购，保留之后所有续购的顺序。每份实际30或31天。
4. 当前套餐剩余时间与剩余额度放弃。新期从操作成功时开始，新到期时间为该时刻加上所有尚待启用订单的实际天数之和。
5. 例如当前剩20天、已续购30天，合计剩50天：重置后新期完整30天；若另有31天续购排队，则总到期为61天后，当前新期30天，后续31天仍待启用。
6. 赠送、手动延长、退款中、购买记录缺失或来源无法唯一确定时拒绝自动重置，不凭时间补造购买权益。

## 实现边界

- 用户订阅页在套餐操作旁显示按钮，打开管理员配置的可信商城确认页；由商城登录会话决定用户身份，不信任浏览器提交的 user_id 或购买码。
- 新设置 `subscription_reset_url` 默认为空；配置完整 HTTPS 商城入口，例如 `https://www.yunqiao.me/subscription-reset`。该入口使用现有可信嵌入页登录机制，必须由管理员核对域名后配置。
- 商城在预览和提交时都重新核对订单，提交带 CSRF 与短期签名预览；调用仅允许完整管理员权限的原子后台接口。
- `POST /api/v1/admin/subscriptions/:id/activate-renewal` 在一个数据库事务中校验原状态、锁定旧订阅、验证兑换码、撤销旧期、创建新期并写入持久回执。普通会员不能直接调用该管理员接口。
- `GET /api/v1/admin/subscriptions/:id/renewal-activation` 为商城退款和自动重开恢复提供已执行结果；旧订阅已软删除时仍可查询回执。
- 新备注保持原插件的“套餐当前购买码／套餐待启用购买码／原订阅ID”来源链，兼容后续续购、重开与退款判断。
- 重复提交、响应丢失后的重试复用同一操作标识；已消费旧期不得恢复为可用套餐。
- 在途旧请求仍记账到旧期，只有存在重开回执的已撤销订阅允许此类迟到结算，不把旧费用挪入新额度。
- Redis 额度缓存携带订阅ID，并通过版本屏障拒绝过期快照回写；迟到旧期用量不能增加新期缓存额度。
- 保持 `subscription_maintenance.auto_reset_enabled=false`；没有重新启用官方日、周、月自动清零。

## 数据库与发布准备

官方 v0.2.24→v0.2.25 没有新增迁移。本功能新增迁移 `253_quya_subscription_renewal_activations.sql`，创建专用重开回执表；不回填猜测的历史购买次数，不初始化数据库，不更改现有余额和订阅期限。

部署候选应用前必须先按现有迁移管理流程应用并登记253迁移，原因是订阅计费会查询该表。两台应用共用数据库，只执行一次。不能通过打开全量启动初始化来代替受控迁移。

建议发布顺序：备好可回滚的应用与 PHP 文件 → 在测试环境验证253迁移和新接口 → 在共享生产数据库执行并登记253迁移 → 两台服务均部署支持回执和账期缓存的新应用，并等待旧实例的请求与计费队列排空 → 部署包含退款/cron保护的 PHP 配套 → 最后配置 `subscription_reset_url` 开放入口。混合运行旧版期间禁止开放重置，旧版缓存增量尚不能识别订阅ID。

URL留空只隐藏按钮，不是服务端停用开关。需要临时停用或回滚时，同时阻断 PHP 重置页面及 preview/execute API（包括 `/pay` 挂载）。已发生重置后，不能直接恢复缺少回执保护的旧版退款、自动重开或计费代码；必须保留兼容修复、回执表及已执行记录，不回滚已经消费的订单权益。具体步骤见 PHP 配套 README。

PHP 配套来自当前商城实文件，位于本仓库 `integrations/yunqiao-subscription-reset`。补丁只修改相关路由、订单核验、客户端接口、退款/自动任务保护和新页面，发布时须核对基线哈希并保留线上其他改动。
